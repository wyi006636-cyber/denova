# Codex 融合方案评审反馈

> **评审人**：WorkBuddy（齐活林团队，原 PRD + 架构设计产出方）
> **评审对象**：《小说写作工具最终推荐方案 — 约束驱动的 Denova 模块化演进》
> **评审日期**：2026-07-21
> **评审立场**：客观对比，不护短，以"做出最好产品"为目标

---

## 总体评价

**Codex 这份方案的架构成熟度高于我的原始方案。** 它在数据安全、作者控制、复用现有资产、许可证合规、工程务实性上明显更优。但在网文特色功能深度（题材模板/追读力/十一维审查/去 AI 味/可视化 Dashboard）上不如我的方案丰富。

**最优路线应该是：以 Codex 的架构哲学为底座，融合我的网文特色功能。** 不是二选一，而是分层融合。

## 一、最关键的问题（优先讨论）

### 🔴 关键问题 1：Agent 隔离机制 — Codex 是对的，我原方案过度工程

| 维度 | 我的方案 | Codex 方案 |
|------|---------|-----------|
| 隔离方式 | exec.Command 启动独立 agent-worker 二进制子进程 | Eino 现有 Agent/Subagent 全新上下文 |
| 理由 | goroutine 共享内存无法物理隔离 | 小说写作场景下 Writer/Reviewer 都是可信代码，核心隔离需求是上下文隔离而非进程隔离 |
| 代价 | 需编译分发独立二进制，增加复杂度 | 无额外二进制，复用 Denova 现有能力 |

**我认同 Codex。** 我的 exec.Command 方案存在两个问题：
1. **过度工程**：小说写作的 Writer/Reviewer 不是不可信第三方代码，用 Eino 的全新消息上下文就能实现"Reviewer 不读取 Writer 思维过程"的核心隔离目标
2. **安全错觉**：Codex 正确指出"单独启动子进程只能隔离内存，不能限制它读取磁盘或网络，不得称为安全沙箱"。我的方案把进程隔离包装成"安全沙箱"是不严谨的

**修正建议**：采用 Codex 的上下文隔离方案作为默认。只有未来引入不可信第三方 Skill 可执行代码时，才启用 OS 级沙箱（容器/受限账户）。

---

### 🔴 关键问题 2：Profile 抽象 — 这是 Codex 方案最大的产品洞察，我完全缺失

Codex 提出三类创作 Profile：
- `long_serial`（长篇连载）
- `fanqie_short`（番茄短篇）
- `zhihu_salt_short`（知乎盐选短篇）

**这是我的方案完全缺失的维度。** 我只考虑了长篇网文（37 题材模板），忽略了番茄短篇和知乎盐选短篇是**完全不同的创作模式**：
- 长篇：卷→章结构，章节龙骨，伏笔追踪，批量连写
- 番茄短篇：场景/节拍结构，开篇信息密度，冲突及时进入，完整结局
- 盐选短篇：叙事视角，秘密/信息差，反转前置依据，情绪闭环

**用长篇规则硬套短篇是错误设计。** Codex 的"共用引擎 + Profile 表达差异"是正确的抽象。

**修正建议**：完全采用 Codex 的 Profile 抽象。我的 37 题材模板应作为 Profile 内的"题材子分类"，而非顶层结构。

---

### 🔴 关键问题 3：Markdown 唯一真源 vs 多源 — Codex 更清晰

| 维度 | 我的方案 | Codex 方案 |
|------|---------|-----------|
| 真源 | 文件系统 + SQLite + 向量库 + Git（多源） | Markdown 唯一真源，SQLite/向量库只是可重建索引 |
| 风险 | SQLite 数据可能与文件不一致 | 索引删除后可从文件全量重建，不依赖数据库 |
| 作者体验 | 作者改文件可能导致索引不一致 | 作者可直接改 Markdown，系统标记索引过期并重建 |

**我认同 Codex。** "计划不等于事实，只有正文定稿后确认发生的内容才能进入正式连续性资料"这条原则非常重要。我的方案让 SQLite 存储结构化数据（角色状态/伏笔/审查记录）有成为"第二真源"的风险。

**修正建议**：采用 Codex 的真源矩阵。SQLite 只做索引和缓存，所有正式事实只在 Markdown 中。Finalization Service 是唯一合法的正式写入路径。

---

### 🟡 关键问题 4：前端重构力度 — 需要平衡，Codex 偏保守

| 维度 | 我的方案 | Codex 方案 |
|------|---------|-----------|
| 前端策略 | Shadcn UI 重写，Tiptap 编辑器，全新三栏布局 | 复用 Denova 现有 React/TipTap/shadcn，不重写 |
| 理由 | 老板明确要求"重构前端 UI，提升视觉设计" | 现有前端已覆盖大量能力，重写代价高 |
| 风险 | 重写周期长，可能引入回归 | 保守，可能不够美观 |

**这部分我有保留意见。** 老板在原始需求中明确要求"重构前端 UI，提升视觉设计和用户体验，使界面更美观、操作更流畅"。Codex 的"不重写前端"可能与老板诉求冲突。

**修正建议**：折中方案 —— 不重写技术栈（保留 React/TipTap/shadcn），但**重构信息架构和视觉设计**：
- 采用 Codex 的 4 个核心页面结构（作品主页/规划中心/工作台/审稿中心）
- 在现有 shadcn 组件基础上重新设计视觉风格、布局、交互
- 新增 Agent 编排台可视化（DAG 流程图）和 Dashboard（我的方案有 8 个面板）
- 这是"设计重构"而非"技术重写"，工作量可控

## 二、赞同点（Codex 方案明显优于我的方案）

### ✅ 1. 作者确认是不可绕过的定稿边界

Codex 的 ADR-004："自动化最多生成待审产物，文学判断和正式事实归作者"。

我的方案有 Blocking 机制，但没有把"作者确认"上升到宪法级。Codex 的"所有未确认结果只能写入工作区"、"审稿完成不等于正文通过，评分达到阈值也不等于定稿"是更安全的设计。

**完全采纳。**

---

### ✅ 2. Harness 是程序状态机，不是超级 Agent

我的 Harness Agent 系统设计有把 Orchestrator 当成"超级 Agent"的倾向（让它做取舍整合、异常处理、调度）。Codex 正确指出："确定性状态迁移由 Go 代码完成，模型只处理语义任务"。

**完全采纳。** Harness 应该是确定性的 Go 代码状态机，Agent 只在 Stage 内部被调用处理语义任务。

---

### ✅ 3. 复用 Denova 现有 SSE，不引入 WebSocket

我的方案引入 WebSocket 用于 Agent 执行状态实时推送。Codex 明确拒绝："不因新功能额外引入 WebSocket，除非出现 SSE 无法满足的双向实时需求并有性能证据"。

**我认同。** SSE 已经能满足 Agent 状态推送（服务器→客户端单向），WebSocket 是过度工程。

---

### ✅ 4. 延后向量库，先 FTS

我的方案在 MVP 就引入 Embedding/Rerank/BM25 三层回退。Codex 主张"先 FTS 和精确读取，用真实评测决定升级"。

**我认同。** 向量库引入安装复杂度（Embedding 模型/Rerank 服务），MVP 阶段 SQLite FTS5 已经能满足大部分检索需求。应该用真实长篇评测证明 FTS 不足时再引入。

---

### ✅ 5. webnovel-writer v7 理念 vs v6 重型 Story System

我的方案采用了 webnovel-writer v6 的 Story System 主链（`.story-system/` 作为平行真源）。Codex 正确指出这会引入"第二套真源"问题，主张采用 v7 的"文件真源、精准读取、薄流程、自愈"理念。

**我认同。** 平行真源是数据一致性陷阱。v7 的方向更正确。

---

### ✅ 6. Skills 能力契约抽象

Codex 的 capability ID 抽象（如 `ideation.generate-premises`、`outline.build-long-arc`）比我的"直接调用 skill 名称"更解耦。Harness 依赖能力契约，不依赖具体 Skill，这样替换 Skill 不需要修改工作流。

**完全采纳。**

---

### ✅ 7. 许可证意识

这是我方案的重大疏漏。Codex 明确指出：
- webnovel-writer 是 **GPL-3.0**（传染性开源协议）
- 虾评 Skills 需逐项确认授权
- 采用 clean-room 方法论借鉴，不直接复制代码/模板/提示词

我的方案默认"整合虾评 skills"，但没有考虑许可证合规。如果产品要开源（Apache-2.0）或商业化，这是法律风险。

**完全采纳。** 正式发布前必须做许可证审计。

---

### ✅ 8. Phase 0 工程基线与决策冻结

Codex 的 Phase 0（1-2 周）做上游同步、回归测试、许可证矩阵、Schema 冻结。这是我方案缺失的。

**完全采纳。** 在动手写新功能前，先建立回归测试基线和决策冻结，是工程纪律。

## 三、质疑点 / 改进建议（Codex 方案的不足）

### 🟡 改进 1：网文特色功能缺失，需补充

Codex 方案在通用写作流程上很完整，但**网文特色功能几乎空白**。老板要的是"功能更强大"的小说写作工具，以下是必须补充的：

| 缺失功能 | 来源 | 价值 | 建议优先级 |
|---------|------|------|-----------|
| **37 题材模板** | webnovel-writer | 网文作者一键初始化项目框架（大纲/爽点/力量体系/角色卡） | P1 |
| **追读力系统** | webnovel-writer | Hook/Cool-point/微兑现/债务追踪，量化章节吸引力 | P1 |
| **十一维质量审查** | 虾评-小说审校员 | 比Codex的笼统"语义审查"更具体可执行 | P1 |
| **五维去 AI 味** | 虾评-人味写作引擎 | 网文读者极度反感 AI 味，这是刚需 | P1 |
| **六线推演法** | 虾评-多米长篇创作 | 大纲阶段并行推演主线/感情/成长/势力/伏笔/爽点 | P2 |
| **章节施工单** | 虾评-维度化器 | 维度化拆分，每章生成施工指导 | P2 |

**建议**：这些功能应作为 Skill 注册到 Codex 的 Capability Registry，通过 Profile 配置启用。例如长篇 Profile 默认启用追读力和 37 题材模板，盐选短篇 Profile 默认启用反转前置检查。

---

### 🟡 改进 2：可视化不足，需补充 Dashboard 和 Agent 编排台

Codex 的前端只有 4 个核心页面，缺少：
- **Agent 编排台**（DAG 流水线可视化、执行日志实时展示、Skill 配置）— 老板要"交互更便捷"
- **Dashboard**（实体关系图谱、追读力曲线、质量雷达图、伏笔时间线）— 网文作者需要数据可视化辅助决策

**建议**：在 Codex 的 4 页面基础上新增 2 个页面：
- 运行中心（Codex 有提到，但应增强为 Agent 编排台 + DAG 可视化）
- 数据看板（项目概览/实体图谱/追读力/质量雷达/伏笔时间线）

---

### 🟡 改进 3：虾评 Skills 整合方案不够具体

Codex 的"能力注册"抽象很好，但对 11 个虾评 skills 的具体整合方案不够详细。我的方案有完整的映射表：

| 虾评 Skill | 对应 Capability ID | 适用 Profile/阶段 |
|-----------|-------------------|------------------|
| 小说助手 | `continuity.review-facts` | 长篇/事实审查 |
| 深度小说写作法 | `style.advanced-craft` | 通用/写作 |
| 爽点架构生成器 | `outline.build-hooks` | 长篇番茄/大纲 |
| 小说审校员 | `editor.review-eleven-dim` | 通用/审稿 |
| 人味写作引擎 | `style.revise-human-touch` | 通用/润色 |
| 维度化器 | `outline.dimensionize` | 长篇/施工单 |
| 多米长篇创作 | `workflow.longform-master` | 长篇/全流程 |
| 对话风格库 | `character.dialogue-style` | 通用/人物 |

**建议**：在 Codex 的 Capability Registry 基础上，补充这张映射表，明确每个虾评 skill 对应的能力 ID 和适用场景。

### 🟡 改进 4：工期估算差异大，需确认团队规模

| 方案 | 工期 | 假设 |

Codex 的工期更现实。我的 80 人天估算偏乐观，没有充分考虑数据迁移、异常恢复、UI 迭代、模型/Skill 质量评测。

**建议**：采用 Codex 的工期估算。如果老板希望加速，应明确团队规模（2-3 人并行可压缩到 14-20 周）。

### 🟡 改进 5：Tauri 桌面打包延后 — 需确认老板意向

## 五、最终建议：分层融合方案

```

│  - Harness 程序状态机，不是超级 Agent     │

│  - Profile 抽象（长篇/番茄/盐选）         │

│  - Skills Capability 契约                │
│  - 许可证合规（clean-room 借鉴）          │

│ 第二层：融合我的网文特色功能（能力层）      │
│  - 37 题材模板（作为 Profile 子分类）     │

│  - 十一维审查（作为 editor.review 能力）  │
```

## 六、需要老板拍板的关键决策

1. **前端策略**：接受"设计重构不技术重写"（保留 React/TipTap/shadcn，重新设计视觉和布局）？还是坚持 Shadcn UI 完全重写？
2. **桌面打包**：MVP 是本地 Web 服务（浏览器打开）还是 Tauri 桌面应用（双击启动）？
3. **团队规模**：1 人全职（22-30 周）还是 2-3 人并行（14-20 周）？
4. **网文特色功能优先级**：37 题材模板/追读力/十一维审查/去 AI 味，哪些是 P0 必须有？
5. **虾评 skills 获取**：能否获取完整提示词？还是采用 clean-room 方法论自研？

---

> **评审结论**：Codex 方案在架构层明显更优，建议以其为底座；我的方案在网文功能层更丰富，建议作为能力补充。两者融合后的方案，比任何单一方案都更接近老板"功能更强大、更易用、前端更美观"的诉求。
