# 小说写作工具 · 项目设计方案

> 版本：v1.0 ｜ 日期：2026-07-20
> 基础框架：[denova](https://github.com/alfredxw/denova)（Go + React，Apache-2.0）
> 方法论来源：[webnovel-writer](https://github.com/lingfengQAQ/webnovel-writer)、[novelforge-agent](https://github.com/LvPengfei1/novelforge-agent)、[虾评小说写作 Skills](https://xiaping.coze.com/?search=小说)
> 配套调研文档：`denova-调研报告.md`、`research_notes/webnovel-writer-调研报告.md`、`novelforge-agent-调研报告.md`、`xiaping_research_report.md`

## 1. 项目愿景与定位

**一句话定位**：面向中文网文长篇连载的本地优先 AI 创作工作台——以 denova 的工作区架构为骨，以 webnovel-writer 的一致性方法论为魂，以 novelforge-agent 的隔离封包机制为闸，整合虾评生态的写作技能库，实现"从创意到日更"的全流程自动化辅助。

**与三个母项目的差异化**：

| 维度 | denova | webnovel-writer | novelforge-agent | 本项目 |
|---|---|---|---|---|
| 形态 | 通用创作 IDE | Claude Code 插件 | CLI 框架 | **专业网文写作 IDE** |
| 一致性保障 | 上下文工程强，无方法论 | 合同-提交-投影 | 哈希闸门+封包 | **三者融合** |
| 自动化程度 | 半自动（对话驱动） | 半自动（命令驱动） | 低（人工编排） | **全自动流水线+人工闸门** |
| 网文适配 | 弱 | 极强（爽点/伏笔/追读） | 无 | **原生内置** |
| UI | 通用工作台 | 只读面板 | 无 | **重构的写作专用 UI** |

**核心设计哲学**（继承自 webnovel-writer 并扩展）：

1. **大纲即法律，设定即物理，发明需识别**——发生过的事实必须登记、过审、存档；
2. **LLM 负责创作与判断，代码负责确定性校验与记账**——把模型的不确定性关进闸门；
3. **文件是真源，索引是投影**——所有设定落 Markdown/JSON 文件，SQLite/向量库只是可重建的派生视图；
4. **改流程不改代码**——写作流程以 SKILL.md 声明，技能可安装、可组合、可评测。

## 2. 调研结论与取舍矩阵

### 2.1 从 denova 继承（基础框架，保留）

| 资产 | 说明 | 处置 |
|---|---|---|
| Go + Hertz + Eino ADK Deep Agent | 多 Agent builder（ide/interactive/director/config/automation），filesystem+skill 中间件，task 子 Agent 委派 | **保留为 Agent 基座** |
| Context Source / Ledger 体系 | 每个注入片段有来源、用途、大小上限、放置位置；全量审计可视化 | **保留并扩展**（增加"合同"类来源） |
| 工作区变更账本 workspacechange | Change group + Diff + 行内评论 + 跨重启 Undo/Redo | **保留，作为 AI 改稿的审阅界面** |
| SKILL.md 声明式工作流 | 自然语言定义写作流程，UI 可安装 zip/URL/GitHub | **保留并作为虾评 skills 的承载格式** |
| go-git 版本快照 | create/diff/restore + 自动保存 | **保留** |
| 纯文件工作区（ideas.md / CREATOR.md / chapters/ / setting/ / .denova/） | 无数据库，遍历目录+正则识别章节 | **保留为真源，增加 SQLite 索引层** |
| React 19 + TipTap + shadcn/ui + Tailwind 4 | 编辑器与组件体系 | **保留技术栈，重构信息架构** |
| 游戏模式（interactive/，71 个 Go 文件） | 互动文字冒险 | **冻结/裁剪**（见 §9 风险） |

### 2.2 从 webnovel-writer 吸收（方法论，移植）

| 方法论 | 价值 | 移植方式 |
|---|---|---|
| **合同-提交-投影三段式** | 写前约束合同化、写后事实入账、派生只读视图 | 落地为 `.story-system/` 合同树 + CHAPTER_COMMIT + 五路投影 |
| **防幻觉三定律** | 解决遗忘/幻觉/失控 | 注入 Agent 系统提示与 Reviewer 检查项 |
| **CBN/CPN/CEN 结构化章纲节点 + 本章禁区** | 章纲完成度可机器校验 | 章纲 schema 增加 nodes/forbidden_zones 字段，写后 fulfillment 校验 |
| **伏笔紧急度公式 + ≤5 条并发** | `(已过章/目标章)×层级权重`，🔴🟡🟢 分级 | 数据层实现为 SQLite 表 + 定时重算 |
| **追读力体系**（钩子5型/爽点密度红线/微兑现7类/债务机制） | 网文节奏核心，欠读者的爽点要还 | 落地为 pacing 模块 + chase_debt 表 |
| **Strand Weave 三线织网** | Quest 55-65% / Fire 20-30% / Constellation 10-20% | 章纲字段 + strand_tracker 状态 |
| **充分性闸门 + 分波次初始化问答** | 先收集再生成，创意约束包制造差异化 | 新书向导（§6.3） |
| **记忆三层**（Working/Episodic/Semantic 7桶带状态降级） | 长篇上下文衰减 | 与 denova context 体系对接（§4.2） |
| **Anti-AI 终检**（八大癖好+替代速查） | 去 AI 味 | 与虾评"人味写作引擎"合并为质量门禁 |
| **拆书只提取模式、严禁污染 canon** | 灵感来源安全复用 | 拆书 Skill + `do_not_copy` 红线 |

### 2.3 从 novelforge-agent 吸收（Agent 架构，强化）

| 机制 | 价值 | 移植方式 |
|---|---|---|
| **哈希锁定的批准闸门** | 四份正本版本+SHA-256，正本一变写作闸门自动关闭 | 扩展 denova 资料库：大纲/设定类 LoreItem 增加 approved_hash，写作前置校验 |
| **每章全新 writer / 独立 reviewer 双重隔离** | 防上下文漂移、防自评偏差、防照单写作 | 利用 Eino ADK `task` 子 Agent 委派实现 fresh-per-chapter |
| **写审不对称信息设计** | 写作包不含审稿清单，审稿包不含写作推理 | 封包构建器内置信息策略 |
| **manifest.json 状态机** | `prepared→drafted→review_prepared→reviewed`，封包过期自动失效 | 章节流水线 run 状态持久化（复用 denova checkpoint） |
| **白名单封包 + 缺料回路** | 上下文最小化、可审计；`NOVELFORGE_MISSING_CONTEXT:` 缺口报告 | 与 denova Source 体系合并：显式声明为主，RAG 检索为补充兜底 |
| **审稿三遍法**（整章复述→近3章同构比较→语言）+ 反检测器路线 | 成熟的审稿方法论 | Reviewer Agent 的标准 prompt |
| **章节龙骨**（300-800字，状态变化+后续约束） | 防矛盾最小记忆单元 | 并入章节摘要 YAML 头规范 |
| **章后同步检查表机器化** | novelforge 的短板（靠自觉） | **本项目补齐**：同步步骤做成确定性代码+校验，漏同步阻断下一章 |

### 2.4 从虾评生态整合（技能库，按需）

分层整合策略（详见 §7）：

- **骨架层**：多米的长篇小说创作（7 阶段工程 SOP + 6 题材手册）
- **记忆层**：小说助手（记忆文件模板）、小说框架维度化器（脚本机械比对 + LLM 语义判断）
- **生成层**：黄金开篇大师（三章七钩子量化规则）、人物塑造大师（五维塑造法）、小说爽点架构生成器（763KB 网文知识库）
- **质量门禁层**：小说审校员（100+ 铁律，需拆维度）、人味写作引擎（去 AI 味）、深度小说写作法（文学技法）

## 3. 总体架构设计

### 3.1 架构总览

```
┌─────────────────────────────────────────────────────────────────┐
│                        前端（React 19 + Vite）                    │
│  写作台 │ 新书向导 │ 流水线控制台 │ 设定中心 │ 数据面板 │ 技能市场  │
├─────────────────────────────────────────────────────────────────┤
│                     API 层（Hertz，REST + SSE）                   │
├──────────────┬──────────────────────┬───────────────────────────┤
│  Agent 层    │   流水线引擎          │   应用服务层               │
│  (Eino ADK)  │   (Pipeline Engine)  │   (book/lore/export/...)  │
│              │                      │                           │
│  orchestrator│  状态机+闸门+重试      │  章节/资料库/导出/导入      │
│  ├─ planner  │  run-ledger 断点续跑  │  版本管理/自动化/技能管理    │
│  ├─ writer   │                      │                           │
│  ├─ reviewer │                      │                           │
│  ├─ data     │                      │                           │
│  └─ style    │                      │                           │
├──────────────┴──────────────────────┴───────────────────────────┤
│                       数据层                                     │
│  文件系统（真源）          │  SQLite 索引（投影）  │  向量库（检索） │
│  chapters/ setting/       │  entities/foreshadows/ │  摘要+场景切片 │
│  .story-system/ .denova/  │  strands/chase_debt/   │  embeddings   │
│                           │  state_changes/...     │               │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 关键架构决策

**决策 1：Fork denova 并保持上游可同步性**
- 新建独立仓库，以 denova 为 upstream remote；所有修改收敛在新增的 `internal/novel/`、`internal/pipeline/`、`web/src/features/novel-*` 目录，尽量不改动 denova 原有文件；
- denova 处于 Beta 高频迭代期（几乎每日提交），保持合并通道可持续吸收其上下文工程与 UI 改进；
- 游戏模式（`internal/interactive/`）不在第一阶段范围内，保留代码但从前端入口隐藏，避免维护分叉。

**决策 2：文件真源 + SQLite 投影，而非引入全量数据库**
- denova 的纯文件工作区是核心资产（可读、可 git、可人工编辑），不破坏；
- 新增 `index.db`（SQLite，存于 `.denova/`）存放结构化追踪数据：实体、状态变更、伏笔、Strand、爽点债务、章节提交记录——全部由 CHAPTER_COMMIT 投影生成，**可随时删除重建**；
- 向量检索作为白名单封包的召回兜底（novelforge 缺召回、webnovel-writer 缺精确性的互补方案）。

**决策 3：Agent 编排沿用 Eino ADK，不引入 LangChain/CrewAI**
- denova 已基于 Eino ADK Deep Agent 建好五类 Agent builder、filesystem/skill 中间件、task 委派——novelforge 的 writer/reviewer 隔离用 `task` 子 Agent 即可实现（每次委派 = 全新上下文实例）；
- 流水线引擎（状态机、闸门、重试）用 Go 自研确定性代码实现，对应 webnovel-writer 的 Python 数据层哲学：**LLM 创作，代码记账**。

**决策 4：写作流程全部 SKILL.md 化**
- 内置技能：新书初始化、卷纲规划、章纲生成、单章写作（轻/标准/重三档）、审稿、润色去AI味、拆书、伏笔体检、爽点诊断；
- 虾评技能经适配层转换为 denova SKILL.md 格式后进入技能市场；
- 用户可在 UI 中创建/安装/编辑技能，形成生态。

## 4. 核心子系统设计

### 4.1 章节流水线引擎（Pipeline Engine）——本项目的心脏

融合 webnovel-writer 的 9 步关卡流水线与 novelforge 的 manifest 状态机：

```
┌──────────────────────────────────────────────────────────────┐
│  单章流水线（run-ledger 记录每步结果，失败只补跑失败步骤）        │
│                                                              │
│  ① 预检 ──→ ② 合同刷新 ──→ ③ 封包构建 ──→ ④ 起草(writer)     │
│  占位符扫描   章纲+时间线     白名单+RAG      全新子Agent       │
│  闸门状态     承接校验        哈希锁定        缺料→③回路        │
│      │                                            │           │
│      ▼                                            ▼           │
│  ⑨ 同步投影 ←── ⑧ 数据提取(data) ←── ⑦ 润色+AntiAI ←── ⑤ 审稿 │
│  五路投影      事实/状态/新实体    去AI味终检      (reviewer)   │
│  git快照       消歧>0.8自动       只改表达        三遍法        │
│                │                            blocking?        │
│                ▼                            │ 是→定点修复/    │
│           CHAPTER_COMMIT ◄──────────────────┘   人工裁决      │
│           (accepted/rejected 判定，accepted 才投影)            │
└──────────────────────────────────────────────────────────────┘
```

**与 novelforge 的关键差异（自动化补齐）**：
- 每章 job 由引擎自动生成（章纲 → 封包白名单自动推导：本章出场角色卡+相关设定+最近N章摘要+紧急伏笔），人工只需在闸门处点"批准"；
- 章后同步（⑨）是确定性代码：状态账本、伏笔账本、时间线、关系矩阵由 data-agent 提取结果自动写入并校验，漏同步则下一章预检阻断——解决 novelforge "靠纪律兜底" 的短板。

**三道闸门**（全部机器可校验）：
- **prewrite**：四正本哈希（总纲/设定集/文风/卷合同）+ 章纲完整性（CBN/CPN/CEN 节点数、禁区条数、时间锚点）；
- **precommit**：reviewer 无 blocking + 必覆盖节点全覆盖 + Anti-AI 终检通过；
- **postcommit**：五路投影全部成功，失败可单独 retry。

### 4.2 上下文工程（Context Engine）

在 denova Source/Ledger 体系上扩展，实现 webnovel-writer 记忆三层 + novelforge 白名单：

| 记忆层 | 实现 | 注入策略 |
|---|---|---|
| Working | 本章合同（章纲+禁区+节点）+ 最近 3 章摘要 + 主角状态卡 | 常驻，StableContextParts 前置吃 prompt cache |
| Episodic | SQLite 近期状态/关系/出场证据（章节窗口过滤） | 按本章出场实体检索注入 |
| Semantic | memory 7 桶（story_facts/world_rules/timeline/open_loops/reader_promises/relationships/character_state），每条带 active/outdated/contradicted/tentative 状态 | 按章纲实体命中注入，非全量 |
| 检索兜底 | 向量库（章节摘要+场景切片 embedding）+ ripgrep 关键词 | writer 报缺料或 auto 模式触发 |

**封包格式**（继承 novelforge）：每个来源 `--- SOURCE BEGIN (path, lines, sha256, purpose) ---` 包裹，Context Ledger 全量审计，前端可视化每轮注入。

**不对称信息策略**：写作封包不含审稿清单与近章全文（防照单写作）；审稿封包不含写作推理（防辩护偏差），含 ≤3 份近章材料做同构比较。

### 4.3 网文一致性系统（Story Consistency System）

**数据模型**（SQLite 投影表）：

```sql
entities(id, name, type, aliases, first_chapter, card_path)        -- 实体登记（发明需识别）
state_changes(id, chapter, entity, field, old, new, confidence)   -- 状态变更（消歧置信度）
foreshadows(id, content, layer, planted_ch, target_ch, status,    -- 伏笔（层级1-3，紧急度重算）
            urgency, weight)
hooks(id, chapter, type, strength, responded_by)                  -- 钩子5型+回应追踪
payoffs(id, chapter, kind, grade, source_debt)                    -- 爽点/微兑现记录（等级C/B/A/S）
chase_debt(id, created_ch, reason, rationale, due_ch, status)     -- 追读债务（欠读者要还）
strand_tracker(chapter, strand)                                   -- 三线织网追踪
chapter_commits(chapter, status, blocking_cnt, missed_nodes,      -- 提交记录
                word_count, summary_path, created_at)
timeline(id, chapter, time_anchor, span, gap_from_prev, countdown)-- 时间线硬约束
```

**内置红线校验器**（确定性 Go 代码，不走 LLM）：
- 时间线单调递增（回跳未标闪回 → 阻断）；
- 相邻章 CEN→CBN 承接断裂 → 警告；
- 伏笔并发 >5 条 → 规划警告；🔴 超期伏笔 → 写前必处理提示；
- 连续 3 章无爽点 / 每 10 章无 B 级爽点 → 追读警报；
- Quest 线连续 >5 章 / Fire 断档 >10 章 / Constellation 断档 >15 章 → 织网警报；
- 能力回退/跳级（realm 比对）→ blocking。

**Reviewer Agent 检查维度**（三遍法 + 五维）：
1. 第一遍整章复述：人物目的/阻力/选择/代价/不可逆变化是否成立；
2. 第二遍同构比较：与近 3 章的叙事功能是否重复（解法/信息路径/关系载体/情绪释放/结尾压力）；
3. 第三遍语言：文风一致性、Anti-AI 检查；
4. 五维一致性：设定冲突、角色 OOC（含知识边界）、时间线、伏笔处理、节奏红线；
5. 输出：blocking（必修）/ major（建议修）/ minor（润色级）三级，blocking 只跑一轮后交人工裁决——避免无限重写循环（novelforge 无终止条件的教训）。

### 4.4 Skills 体系（技能引擎）

完全复用 denova 的 SKILL.md 加载机制，内置技能集：

| 技能 | 来源 | 功能 |
|---|---|---|
| `novel-init` | webnovel-writer 方法论 | 7 步分波次初始化：灵感拆书→故事核→角色骨架→金手指→世界观→创意约束包→确认 |
| `volume-plan` | 同上 | 卷三件套（节拍表/时间线/卷纲骨架）+ 总纲写回 |
| `chapter-plan` | 同上 | 章纲生成（CBN/CPN/CEN+禁区），批量 10 章/批 |
| `chapter-write` | denova 已有基础上强化 | 单章流水线（§4.1），轻/标准/重三档 |
| `chapter-review` | novelforge 三遍法 | 独立审稿 |
| `style-polish` | 虾评·人味写作引擎 + Anti-AI | 去 AI 味润色（只改表达不改事实） |
| `book-deconstruct` | webnovel-writer | 拆书提取模式，do_not_copy 红线 |
| `foreshadow-audit` | 自研 | 伏笔体检报告（紧急度/超期/并发） |
| `pacing-doctor` | 自研 + 虾评爽点知识库 | 爽点节奏诊断与修复建议 |

**虾评技能适配层**（`internal/skill/import/`）：
- 下载 zip → 安全检查（零宽字符水印清洗、体积拆分：审校员 196KB 单文件需按十二维拆成 references）→ frontmatter 规范化 → 注册进技能市场；
- 虾评 skills 全部是标准 Agent Skills 规范（SKILL.md + references/ + scripts/），与 denova 原生兼容，转换成本低；
- **注意版权风险**：虾评包内无 LICENSE，内置发布需逐一评估，默认走"用户自行安装"路径规避。

## 5. 数据模型与工作区结构

在 denova 工作区布局上扩展（新增部分以 ★ 标注）：


## 6. 前端 UI/UX 重构方案

### 6.1 现状问题（调研结论）

denova 前端是通用工作台：Activity Bar + 章节树 + TipTap 编辑器 + Agent 面板。问题：① 写作流水线状态不可见，用户不知道"这章进行到哪一步"；② 网文专用数据（伏笔/爽点/时间线）无界面；③ 已知卡顿 issue；④ App.tsx 根组件臃肿。

### 6.2 信息架构（写作专用重排）

```
┌────────────────────────────────────────────────────────────┐
│ 顶栏：书名 │ 今日字数 │ 连载日历 │ 流水线状态条 │ 设置          │
├──────┬──────────────────────────────────┬──────────────────┤
│ 导航  │        中央工作区                  │   右侧面板        │
│      │  （按模式切换）                    │                  │
│ 写作  │  ┌─写作台：章节树+TipTap+AI 续写    │  Agent 对话      │
│ 大纲  │  ├─大纲板：总纲/卷纲/章纲三级联动    │  （可切：上下文   │
│ 设定  │  ├─流水线：单章 9 步进度+闸门审批    │   分析/变更审阅/  │
│ 面板  │  ├─设定中心：角色卡/世界观/资料库    │   审稿报告）     │
│ 技能  │  ├─数据面板：伏笔/爽点/Strand/时间线 │                  │
│ 版本  │  └─技能市场：内置+虾评+自建         │                  │
└──────┴──────────────────────────────────┴──────────────────┘
```

**六大核心界面**：

1. **写作台**（Editor）：保留 TipTap + 中文衬线排版；新增——章节侧边栏显示本章合同摘要（目标/节点/禁区）、写后显示 fulfillment 覆盖结果、AI 变更走 workspacechange Diff 审阅流；
2. **新书向导**（Init Wizard）：分步表单化 7 步问答（故事核→角色→金手指→世界观→创意包），每步 AI 生成候选 + 用户选择，充分性闸门进度条，最后一致性复述确认；
3. **流水线控制台**（Pipeline）：单章 9 步可视化进度（步骤条 + 每步耗时/token），闸门处"批准/打回"按钮，reviewer 报告分级展示（blocking 红/major 黄/minor 灰），断点续跑一键重试；
4. **设定中心**（Story Bible）：角色卡（含 OOC 警戒/镜像对抗字段）、世界观、势力、时间线可视化（横向泳道图）、关系图谱（实体图谱可视化）；
5. **数据面板**（Dashboard）：伏笔清单（🔴🟡🟢 紧急度排序）、爽点密度曲线（近 30 章）、Strand 三线占比堆叠图、追读债务台账、字数/更新日历热力图；
6. **技能市场**（Skills）：内置技能 + 一键导入虾评技能（URL/zip）+ 自建技能编辑器（Monaco）。

### 6.3 设计原则

- 沿用 denova DESIGN.md 设计系统（`--nova-*` token、4px 栅格、深浅主题、WCAG AA），视觉重构集中在**信息密度重排**而非推翻设计体系；
- **闸门即界面**：所有需要人工裁决的点（创意包选择、blocking 冲突、消歧 pending、打回重写）统一进"收件箱"模式，一次处理一批；
- **少打扰**：AI 默认全自动推进，只在闸门和异常时浮出；
- 性能：章节树虚拟滚动（react-virtuoso 已有）、编辑器分片渲染、App.tsx 按 feature 拆分 zustand store——顺带修复 denova 已知的卡顿问题。

## 7. 虾评 Skills 整合方案

### 7.1 整合架构

```
虾评平台 (xiaping.coze.com)
   │  公开 API：/api/skills?search=小说 │ /skill/<id>/agent.md（含 zip 直链）
   ▼
适配层 internal/skill/import/
   ① 下载+解压 ② 安全清洗（零宽字符/体积拆分/脚本静态扫描）
   ③ frontmatter 规范化（补 name/description/trigger）
   ④ 冲突检测（与内置技能重名/重复触发词）
   ▼
技能注册表（内置 9 + 虾评适配 N + 用户自建）
   ▼
Eino ADK Skill 中间件 → 各 Agent 按需挂载
```

### 7.2 分层整合清单（已实测精读）

| 层 | 虾评技能 | 整合方式 |
|---|---|---|
| 骨架层 | 多米的长篇小说创作（4.5分） | 7 阶段 SOP 融入流水线引擎默认流程；6 题材手册作为初始化时的题材模板 |
| 记忆层 | 小说助手（4.6分） | 记忆文件模板并入 semantic memory 7 桶 schema |
| 记忆层 | 小说框架维度化器（4.6分） | "脚本机械比对+LLM 语义判断"范式直接作为 data-agent 的实现模式；两个 Python 脚本改写为 Go |
| 生成层 | 黄金开篇大师（4.4分） | 三章七钩子量化规则写成确定性 checker（前3章背景≤300字、对话≤40%、每章≥1小高潮） |
| 生成层 | 人物塑造大师（4.4分） | 五维塑造法融入角色卡模板；OOC checker 逻辑并入 Reviewer |
| 生成层 | 小说爽点架构生成器（4.3分） | 763KB 知识库拆分为 references，供 pacing-doctor 技能按需加载；**先做零宽字符清洗** |
| 质量层 | 小说审校员（4.6分） | 196KB 按十二维拆分，作为 review 技能的 references 按需加载 |
| 质量层 | 人味写作引擎（4.4分） | 与 Anti-AI 终检合并为 style-polish；其 frontmatter 内嵌 eval_cases 的写法引入技能评测体系 |
| 质量层 | 深度小说写作法（4.6分） | 文学技法库作为润色 references（注意其内容提炼自出版书籍，仅用户自装） |

### 7.3 评测体系

借鉴虾评的 SBI 评测与人味引擎的 eval_cases：每个内置技能附带评测断言（如"生成的章纲必须含 CBN/CPN/CEN"），CI 中用小样例回归，防止技能/模型升级导致质量回退。

## 8. 技术选型建议

| 层 | 选型 | 理由 |
|---|---|---|
| 后端语言 | **Go 1.26**（沿用 denova） | 单二进制分发、并发友好、上游可同步 |
| HTTP 框架 | CloudWeGo Hertz | denova 现有 |
| Agent 编排 | **CloudWeGo Eino ADK**（Deep Agent + task 委派） | denova 基座；fresh-per-chapter 用子 Agent 天然实现 |
| LLM 接入 | OpenAI 兼容接口（DeepSeek/通义/Kimi/Claude 等自配） | denova 现有，用户自带 Key |
| Embedding | OpenAI 兼容接口可配；无 Key 回退 ripgrep/BM25 | 参考 webnovel-writer 降级策略 |
| 结构化存储 | **SQLite**（modernc.org/sqlite 纯 Go 驱动） | 投影层，零部署 |
| 向量检索 | SQLite-vec 或本地余弦计算（小规模够用） | 避免重依赖 |
| 版本控制 | go-git v5 | denova 现有 |
| 前端 | **React 19 + TypeScript + Vite + Tailwind 4 + shadcn/ui** | 沿用，降低重构成本 |
| 编辑器 | TipTap 3 | 沿用 |
| 图表 | 新增 **ECharts**（爽点曲线/时间线泳道/关系图谱） | 中文文档好，大数据量性能强 |
| 状态管理 | zustand（按 feature 拆 store）+ react-query | 沿用并重构 |
| AI 对话流 | Vercel AI SDK + 自定义 SSE transport | 沿用 |
| 导出 | 新增 epub（go-epub）/ docx（unidoc 或模板渲染） | 补齐 denova 仅 txt 的短板 |
| 测试 | Go test + Vitest（沿用）；新增流水线行为 eval | 继承 denova 工程纪律 |

**不选的**：LangChain/CrewAI（与 Eino 重复且引入 Python 运行时）、PostgreSQL（违背单机定位）、Electron（denova 的浏览器+PWA 形态已够用）。

## 9. 实施路径

### 阶段总览（建议节奏：4 个里程碑，每里程碑 3-5 周）

```
M1 地基（fork+裁剪+数据层）──→ M2 方法论落地（合同+流水线+审稿）
        ──→ M3 网文增强（伏笔/爽点/记忆+数据面板）──→ M4 生态与体验（技能市场+UI 打磨+导出）
```

### M1 · 地基（Fork 与数据层）

| # | 任务 | 验收标准 |
|---|---|---|
| 1.1 | Fork denova，建立 upstream 同步策略与目录隔离规范（`internal/novel/`、`web/src/features/novel-*`） | 可合并 upstream 最新提交无冲突 |
| 1.2 | 裁剪：前端隐藏游戏模式入口；确定保留模块清单 | 写作模式全功能正常 |
| 1.3 | SQLite 投影层：`internal/novel/indexdb/`（§4.3 全部表 + 迁移机制 + 从文件重建命令） | `denova reindex` 可从零重建 |
| 1.4 | 工作区扩展：`.story-system/` 合同树 schema + `.denova/summaries|memory|pipeline/` 目录 | schema 文档 + 读写 API |
| 1.5 | 性能修复：章节树虚拟化、App.tsx 拆分 | 复现并关闭 denova 卡顿 issue 的本地场景 |

### M2 · 方法论落地（合同-提交-投影 + 流水线）

| # | 任务 | 验收标准 |
|---|---|---|
| 2.1 | 流水线引擎 `internal/pipeline/`：状态机、run-ledger、断点续跑、三道闸门 | 单章全流程跑通，杀进程后可续跑 |
| 2.2 | 章纲 schema 升级：CBN/CPN/CEN 节点 + forbidden_zones + 时间锚点；chapter-plan 技能 | 章纲缺字段被 prewrite 闸门拦截 |
| 2.3 | 封包构建器：白名单自动推导 + 哈希锁定 + 不对称信息策略 + 缺料回路 | Context Ledger 可审计每个来源 |
| 2.4 | writer/reviewer/data 三个 task 子 Agent（fresh-per-chapter）；reviewer 三遍法 prompt | 审稿报告含 blocking 分级 |
| 2.5 | CHAPTER_COMMIT + 五路投影（state/index/summary/memory/vector）+ accepted/rejected 判定 | blocking>0 时自动 rejected |
| 2.6 | 哈希批准闸门：总纲/设定/文风/卷合同四正本 | 正本改动后写作闸门自动关闭 |
| 2.7 | 新书向导前端（7 步分波次 + 充分性闸门） | 信息不足无法生成总纲 |

### M3 · 网文增强（追读力与记忆）

| # | 任务 | 验收标准 |
|---|---|---|
| 3.1 | 伏笔系统：紧急度定时重算、并发上限、🔴超期写前必处理 | 伏笔体检报告技能可用 |
| 3.2 | 追读力模块：钩子追踪、爽点密度红线校验、chase_debt 债务机制、Strand 三线追踪 | 连续3章无爽点触发警报 |
| 3.3 | 记忆三层接入 context 引擎（Working/Episodic/Semantic 7桶+状态降级） | 50 章后角色状态不漂移（eval 验证） |
| 3.4 | 时间线/能力红线校验器（Go 确定性代码） | 时间回跳未标闪回被阻断 |
| 3.5 | 数据面板前端：伏笔清单/爽点曲线/Strand 占比/时间线泳道（ECharts） | 面板数据与 index.db 一致 |
| 3.6 | Anti-AI 终检 + 虾评人味引擎整合（style-polish 技能） | 终检 fail 不提交 |
| 3.7 | 技能评测体系（eval_cases + CI 回归） | 内置技能全部带评测断言 |

### M4 · 生态与体验

| # | 任务 | 验收标准 |
|---|---|---|
| 4.1 | 虾评适配层：下载/清洗/规范化/冲突检测 + 技能市场 UI | 一键安装 9 个实测技能 |

### 关键里程碑定义

- **M3 完成 = 差异化成立**：追读力与伏笔体系是市面上其他工具没有的；
- **M4 完成 = 可公开发布**。

## 10. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| denova Beta 期破坏性变更（v0.3.0 已有先例） | 高 | 目录隔离 + 每月定点同步 upstream + 同步前跑集成测试；必要时冻结版本独立演进 |
| denova 单人项目（bus factor） | 中 | Fork 即拥有全部代码；Eino/Hertz 生态小众但文档完整 |
| 虾评技能版权不明（无 LICENSE） | 高 | 默认用户自装路径；内置发布前逐一取得授权或仅内置自研技能 |
| 流水线 token 成本高（每章 5 个 Agent 角色） | 中 | 轻/标准/重三档；缓存友好的 StableContextParts；支持廉价模型分级（规划用强模型、提取用弱模型） |
| 一致性指标无量化基线 | 中 | M3 建立 eval 集（伏笔回收率/OOC 检出率/时间线错误率/爽点达标率），每次发版回归 |
| SQLite + 文件双写一致性 | 低 | 投影只读、commit 事务内生成、reindex 可重建 |
| 范围蔓延（游戏模式/协作/云同步） | 中 | 明确 v1 不做：多人协作、云同步、游戏模式增强 |
