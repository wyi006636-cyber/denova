# ADR-CS-001: CandidateSet v1

## Status

**Accepted v1** — 2026-07-21

This decision approves CandidateSet contract `v1`. It is a controlled-evolution boundary, not a permanent freeze. Changes to identity, state vocabulary, transition rules, lineage, hash binding, or author authority require a superseding ADR, a new contract version, compatibility rules, and a migration path.

## Context

One generation is sufficient for many ordinary stages, while a resolved Profile, QualitySpec, or CandidatePolicy may justify multiple candidates at a valuable creative node. Candidate count is therefore governed by resolved contract data and evaluation evidence, never by hard-coded platform folklore. Every candidate remains a review artifact rather than formal manuscript truth.

Without stable identities, byte hashes, comparison evidence, and explicit author decisions, candidate generation becomes unauditable extra model calls. Mixing candidates is especially risky because copied segments can lose their parent source. CandidateSet must preserve the chain from workspace and run through the exact generated bytes and the eventual Author Finalization handoff.

## Decision

### Identity and binding chain

A CandidateSet v1 record uses `contract.kind=denova.candidate-set`, `contract.version=v1`, and schema `candidate-set-v1.schema.json`. It has a stable `candidate_set_id` and binds all of these identities and versions:

- workspace ID, revision, and hash;
- run ID and run contract version;
- stage ID, stage type, and stage contract version;
- artifact ID, artifact type, artifact contract version, and hash;
- Source Manifest ID, version, and hash;
- resolved Profile ID, contract version, and hash;
- resolved QualitySpec ID, revision, contract version, and hash;
- resolved CandidatePolicy ID, version, requested count, key-node decision, and rationale;
- for each candidate, its stable ID, Artifact identity, content hash, Source Manifest binding, model/provider identity and version, Skill identity/version/hash plus stable Capability ID, Profile binding, QualitySpec binding, and creation time.

SHA-256 is represented as 64 lowercase hexadecimal characters. A validator must recompute hashes from canonical referenced bytes; a matching string shape is not proof that bytes match.

Ordinary stages may contain one candidate. A key node uses multiple candidates only when the resolved Profile, QualitySpec, or policy requires it. A one-candidate set still passes through `compared`, so the evaluation and its evidence are recorded.

### Exhaustive lifecycle

The complete state vocabulary is `open`, `compared`, `author_selected`, `mixed`, `rejected`, `finalized`, and `archived`. The only transitions are:

- `open -> compared`;
- `compared -> author_selected | mixed | rejected`;
- `author_selected -> finalized | archived`;
- `mixed -> finalized | archived`;
- `rejected -> archived`;
- `finalized -> archived`.

There is no catch-all transition. Unknown states or transitions fail explicitly. `rejected` can never finalize. `archived` is terminal. Each transition records stable ID, actor ID/type, reason, timestamp, and from/to state. The schema closes the vocabulary and legal transition pairs; semantic validation additionally verifies that history starts at `open`, is contiguous, has no duplicate transition ID, and ends at the record's current state.

`compared` and every later state require a structured evaluation. The evaluation names every compared candidate, records an actor and timestamp, and includes reader-observable criterion evidence for each candidate. A numeric score is optional and cannot replace prose evidence.

`author_selected`, `mixed`, and `rejected` require an author decision with actor, timestamp, and reason. Selection names exactly one candidate; rejection names none; mixing names at least two parent candidates. Models, Skills, reviewers, and Automations cannot create the author decision.

### Mixed lineage

A mixed decision records the composed output hash and an ordered, non-empty segment map. Every selected segment identifies its parent candidate ID, parent candidate content hash, parent byte range, output byte range, and segment content hash. Semantic validation confirms all parents belong to the set, hashes match stored candidate and sliced bytes, ranges are valid and non-overlapping, segments cover the composed bytes in order, and recomposition produces the declared output hash. Failure is a hard validation error, never an inferred parent.

### Stale data and Author Finalization boundary

Validation records each expected and observed hash as `valid`, `stale`, or `hash_mismatch`, with checked time and reason where invalid. Any changed workspace revision, Source Manifest, candidate bytes, Profile, QualitySpec, or policy makes the set stale or mismatched. The old Artifact remains for audit, but it cannot be silently refreshed, compared as current, or finalized; the author must choose a validated rerun or explicitly return to an earlier workflow operation.

Only an author-selected or mixed decision with all bindings valid is eligible for Author Finalization. CandidateSet can mark the handoff `ready` or record a `handed_off` request/receipt identity, but it cannot mutate formal content. Finalization is a separate contract and the sole formal-write authority. `finalized` requires a handed-off receipt bound to the selected or composed content hash. Rejected sets are `not_eligible`.

## Alternatives

### Always generate multiple candidates

Rejected. It raises cost and latency without evidence of benefit; the resolved policy decides count.

### Store only the selected text

Rejected. It loses comparison evidence, rejected alternatives, generation identity, and author-decision provenance.

### Treat mixed output as a new unparented candidate

Rejected. Segment lineage and hashes are required so every selected byte remains attributable.

## Consequences

- Candidate choices and quality gain can be audited without promoting candidates to formal truth.
- A single candidate still incurs an explicit comparison record.
- Mixed output is more verbose because segment provenance is mandatory.
- Cross-reference, transition-history, range, and byte-hash equality require semantic validation beyond JSON Schema.

## Migration

P0-T05 creates documentation and schemas only; it rewrites no workspace data. A v1 reader rejects malformed or unknown authoritative records for managed mutation while preserving their bytes for safe inspection/export. A future version must provide a superseding ADR, schema compatibility, previewable provenance-preserving conversion, and rollback before rewriting CandidateSet records.

## Validation

`schema/candidate-set-v1.schema.json` is the normative shape and closed-vocabulary companion. Draft 2020-12 validation must accept an in-memory full chain through mixed selection and finalization, and reject missing source identity, illegal transitions, missing mixed lineage, and malformed actor/evidence records. A semantic validator must recompute hashes, validate contiguous history/current state, candidate references, segment ranges/recomposition, and finalization receipt binding. `git diff --check` and exact-scope review are required.

## Supersedes
